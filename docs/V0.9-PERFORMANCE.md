# v0.9.0 第 5、6、8 項改善驗證

基準來源：v0.8.0（`47c122e8ed7d3067d9790058308f359c2c76c5d7`）。測試環境：本機 Windows x64、.NET SDK 10.0.402；整合測試使用 Portable Git 2.56.0.windows.3。各次原始 TRX 與完整套件報告隨 Release 驗證附件提供。

## 第 5 項：大型衝突編輯

固定案例包含 200,000 行一般內容與一個小型衝突，輸入字串在量測前建立。`GC.GetAllocatedBytesForCurrentThread` 只量受測呼叫在目前執行緒的配置，不是全程記憶體、GPU／原生配置或畫面幀時間。

| 呼叫 | 修正前 | 修正後一次本機結果 | 回歸上限 |
| --- | ---: | ---: | ---: |
| Core 解析（CRLF 內容） | 23,395,328 bytes | 224 bytes | < 100,000 bytes |
| ViewModel 輸入回呼（LF 內容） | 18,595,608 bytes | 968 bytes | < 200,000 bytes |

修正前兩項回歸測試均先失敗；修正後通過。解析改用原字串的 span／位置，只有真正衝突內容才建立字串。超過 65,536 個字元時，輸入回呼立即記錄草稿，停止輸入 150 ms 後背景解析；取消過期工作，僅發布目前結果。採用單一區段只重新核對該區段，保留 CRLF／LF 及 diff3 BASE 驗證。編輯器向綁定回報文字時只取得一次文件字串，避免回呼再次讀取整份文件。

此案例不代表任意大型衝突都只配置 224 bytes：若實際衝突區段很大，OURS／THEIRS／BASE 內容仍需配置。背景延遲不是 150 ms 的總完成承諾。UI 測試另驗證非同步完成、取消過期結果、關閉取消、手動編輯與草稿保留。

## 第 6 項：快照剩餘的程序開銷

固定案例：一個已提交檔案，另有 24 個 rebase 狀態檔；每個狀態檔含 NUL、0xFF、CR、LF。SHA-1 與 SHA-256 各自執行擷取及還原，核對全部原始位元組。

| 指標 | 修正前 | 修正後 |
| --- | ---: | ---: |
| 擷取的 `hash-object` 程序總數 | 26 | 3 |
| 狀態檔還原的逐檔 `cat-file blob` 呼叫 | 24 | 0 |
| 工作檔＋狀態檔的還原批次 | 工作檔原已有 1 批、狀態檔逐檔 | 共 2 批 |

一般工作檔在 v0.8.0 已有批次 hash 與串流還原；本次擴充到狀態檔、符號連結，另共用同次快照的空樹。先暫存擷取的狀態位元組再批次寫入 Git，避免「檢查的內容」與「雜湊的內容」不同；成功、失敗或取消離開時清除該次暫存檔。還原仍核對 blob OID、類型、長度與分隔符，先建立暫存檔／連結再替換。保留路徑、Git 狀態符號連結拒絕、index 鎖、refs 交易及 Unix 執行位元檢查。Unix CI 另外驗證真實符號連結批次還原；Windows 不假設具建立連結權限。

程序數是可重現的結構性成本，並非宣稱端到端耗時同比例縮短。未更改快照格式，未移轉或刪除使用者快照。

## 第 8 項：提交簽章

主畫面的提交選單明確區分沿用設定、`-S`、`--no-gpg-sign`；顯示本次讀取的 Git 合併設定值。互斥旗標在建立快照前拒絕。真實 Git 測試以不存在的 signer 重現失敗，驗證不移動 HEAD、不清除暫存或訊息、不修改 `commit.gpgsign`；明確停用只作用於該次提交，啟用則必須嘗試簽章。既有 SSH 金鑰的簽署／驗章與標籤回歸一併保留。UI 成功提交後回到沿用設定。

參考：[git-commit](https://git-scm.com/docs/git-commit)、[git-hash-object](https://git-scm.com/docs/git-hash-object)、[git-cat-file](https://git-scm.com/docs/git-cat-file)。

## 驗證範圍

完整 Core／Engine／UI、六格 CI、精確 Windows ZIP 的功能測試與隔離桌面測試，由版本控制中的發布流程要求並隨 Release 附上實際結果。本文件只記錄以上固定案例的改善；未將 v0.7.0 的 M4 冷啟動／五組捲動數據當作 v0.9.0 的新量測。原 1.5 秒／16 ms 及其他正式驗收門檻保持不變。執行檔未提供程式碼簽章。
